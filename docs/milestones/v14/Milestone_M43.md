# M43 — Device Registry & Protocol Foundation

**Version:** 0.14.0
**Status:** planned
**Source:** intake 2026-07-21 — device support expansion; UX settled against `docs/mockups/v14-peripheral-ux.html`

## Goal

Eliminate the shotgun surgery required to add a device. Today a new device type means editing about
twelve hardcoded sites across TypeScript, C++ and the IPC protocol, including three separately
declared `pot|button|led` unions that must agree, and two new IPC message kinds per device. After
this milestone there is one registry that every view, the codegen and the parser enumerate; the
wire protocol carries device identity in a field rather than in the message kind; and the pin table
is generated from the authoritative pinout CSV rather than hand-maintained. No new device ships
here — the existing three are migrated onto the new foundation with no behaviour change, so the
refactor is provable before anything depends on it.

## Sprint Tasks

### [x] feat: generate the pin/signal table from the Rev4 pinout CSV (FR-DEV-3)

`PIN_DEFS` in `wiring-panel.ts` is hand-maintained and has drifted twice (v7 pinout accuracy fix,
v9 D28 ADC mapping correction). v14 roughly triples it by adding per-pin bus signal names, where a
wrong entry silently corrupts conflict checking rather than merely mislabelling a pin.

**Affected files:** `scripts/gen-pin-table.ts`, `src/devices/pin-table.gen.ts`, `src/wiring/wiring-panel.ts`, `package.json`

**DoD:**
- A build step reads `daisy-seed-knowledge/doc/Daisy_Seed_Rev4_Pinout.csv` and emits `src/devices/pin-table.gen.ts`.
- Generated entries carry `row`, `side`, `pin`, `label`, `aLabel`, `adc` and per-pin bus signal names drawn from the CSV's I2C/UART/SPI/SDMMC columns.
- The generated table is byte-identical to today's `PIN_DEFS` for all fields that exist today, proving no regression in the D28/A11 and ADC-range corrections.
- `wiring-panel.ts` imports the generated table; the hand-maintained literal is deleted.
- The generated file carries a do-not-edit header and regeneration is wired into the build.

### [x] refactor: replace per-device IPC messages with controlValue/controlSnapshot (FR-DEV-1)

`pot`, `potSnapshot`, `button` and `buttonSnapshot` encode device identity in the message kind, so
every new device adds two more. Device identity moves into an `id` field.

**Affected files:** `emulator/runtime/ipc_server.cpp`, `emulator/runtime/ipc_server.h`, `src/webview/messages.ts`, `src/extension.ts`, `src/controllers/button-store.ts`

**DoD:**
- `controlValue {id, value}` and `controlSnapshot {values}` replace all four message kinds on both sides.
- Adding a device type requires no new IPC message kind.
- Discriminated-union validation (v12/M39) covers the new kinds, including rejection of unknown `id`, non-finite `value`, and out-of-range values.
- Post-deploy state replay sends one `controlSnapshot` rather than per-type snapshots.
- Existing pot and button behaviour is unchanged end to end, verified by the existing integration tests.

### [x] feat: add a connect-time protocol version handshake (FR-DEV-6)

The wire change is breaking. A stale emulator binary against a new extension must fail loudly
rather than silently misbehaving.

**Affected files:** `emulator/runtime/ipc_server.cpp`, `src/ipc/ipc-client.ts`, `src/extension.ts`

**DoD:**
- Both sides exchange a protocol version during the connect phase, within the existing connect-phase timeout (v12/M39).
- A mismatch surfaces an explicit, actionable error naming both versions and the remedy, through the existing notification aggregation path.
- On mismatch the session does not start; no control messages are exchanged.
- A test covers older-emulator and newer-emulator mismatch in both directions.

### [x] feat: introduce the device registry as the single source of truth (FR-DEV-2)

**Affected files:** `src/devices/registry.ts`, `src/controllers/controls-convention-parser.ts`, `src/wiring/controls-writer.ts`, `src/wiring/wiring-panel.ts`, `src/sidebar/controls-editor-panel.ts`

**DoD:**

- A test asserts that adding a registry entry surfaces it in the parser, both editors and the codegen without further edits.

### [x] feat: model attachment as pin, pins, bus or connector (FR-DEV-3)

A peripheral's pin footprint is a function of its selected bus, not a constant — an OLED occupies
D7–D10 on SPI1 but D11–D12 on I2C1. Any model storing a static pin set is wrong.

**Affected files:** `src/devices/attachment.ts`, `src/devices/registry.ts`, `src/wiring/wiring-panel.ts`

**DoD:**
- `attachment` supports `pin`, `pins[]`, `bus` (as `bus → signal map`) and `connector`.
- A bus peripheral's footprint is *derived* from its selected bus on every read, never cached as a constant.
- Conflict computation resolves the footprint of every enabled device and reports each clashing pin with its signal and owner.
- The micro USB connector is addressable as an attachment target.
- Tests cover: bus switch re-mapping a footprint, peripheral-to-peripheral collision, peripheral-to-control collision, and connector attachment.
