# M17 — Controls Editor v3 (v0.3.1)

**Status:** planned  
**Version:** 0.3.1  
**Depends on:** M16 (stable baseline), v2 (existing C2 controller panel + Effect controls)  
**Goal:** Replace the split between "Controller Editor" tab (design) and "Effect controls" section (live) with a single two-mode Controls Editor that infers available controls from the C++ source via the ds-ide:controls convention.

---

## Context

The v2 Controls Editor (M10b) requires the developer to manually declare controls in `controllers.yaml`. In v3, the editor reads the C++ source for a `// ds-ide:controls:begin` … `// ds-ide:controls:end` block (D15), extracts id/kind/pin annotations, and uses `controllers.yaml` for placement only. The same panel serves as the live control interface in Run mode.

---

## Tasks

### T17-1 — Implement C9: ds-ide:controls convention parser

Build a new C1 module (`src/controllers/controls-convention-parser.ts`) that:
- Reads a C++ source file
- Locates the `// ds-ide:controls:begin` … `// ds-ide:controls:end` block
- Parses each `TypeName varname; // ds-ide: id=..., kind=..., pin=...` line
- Returns a list of `{id, kind, pin}` objects and any parse errors
- Returns `{controls: [], missingBlock: true}` if the block is absent

**DoD:**
- Unit tests cover: block found + valid annotations, block found + malformed annotations, block absent, empty block.
- Parser is a pure function (no filesystem I/O — caller passes text string).

### T17-2 — Wire C9 into C1 on project open / deploy

- After `controllers.yaml` is loaded (on open and on deploy), also run C9 on the effect source.
- Send a `controlsConfig` message to C2 containing: `controls[]` (from C++ convention or empty), `placements[]` (from yaml), `missingBlock` flag.

**DoD:**
- On open: C2 receives a populated `controlsConfig` when the convention block is present.
- On open with no block: C2 receives `missingBlock: true`.

### T17-3 — Redesign C2 Controls Editor: two-mode panel

Replace the current "Controller Editor" tab + Effect controls footer section with a single Controls Editor panel that:
- Shows a **mode toggle** in the panel header (Design / Run)
- **Design mode:** canvas with draggable control cards (as in M10b); shows "not in code" indicator for controls present in yaml but absent from C++ convention
- **Run mode:** cards become interactive widgets (slider for pots, button for buttons, LED indicator for LEDs); drag is disabled; IPC messages are sent as before

Fallback: if `missingBlock`, show the diagnostic banner and render controls from yaml only.

**DoD:**
- Design mode: controls from C++ convention appear on canvas; dragging updates yaml placement; Save writes yaml.
- Run mode: pot sliders send `pot` IPC, button clicks send `button` IPC, LED events received correctly.
- Diagnostic banner appears when convention block is absent.
- No regression to existing IPC channels or controllers.yaml behaviour (CR-6).
