# M10 — Virtual buttons, GPIO & LEDs

**Status:** in progress
**Target version:** 0.2.2
**Goal:** Press a virtual button and have the effect respond; trigger an LED from the effect and
see it lit in the UI.

**DoD → AC-11 green** — (a) pressing a virtual button visibly changes the effect output (bypass
toggle); (b) the effect lighting a declared LED lights the virtual LED indicator in the UI.
No regression to AC-1…AC-10. Sprint-close → CHANGELOG + 0.2.2 tag.

---

## Locked scope decisions (pre-implementation review, 2026-06-18)

1. **YAML schema — additive sections.** Keep the existing `controllers:` list as the **pots**
   section (unchanged; v1 files keep loading — CR-6). Add two new top-level sections:
   - `buttons:` — each entry `id`, `label`, `gpio_pin` (Daisy pin number 0–31, matches
     `hw.GetPin(n)`), `mode` (`momentary` | `toggle`, default `momentary`), `active_level`
     (`high` | `low`, default `low` — Daisy buttons are typically active-low with pull-up).
   - `leds:` — each entry `id`, `label`, `gpio_pin`. The **onboard user LED is the declared
     entry with `gpio_pin: 23`** (emulator convention for `hw.SetLed`).
   > Reconciles 03 FR-CT-7's "alongside pots:" wording: `pots:` ≡ the `controllers:` section.

2. **LED output — two capture paths, both keyed to a declared `gpio_pin`.**
   - `DaisySeed::SetLed(bool)` → lights the declared onboard LED (`gpio_pin 23`). Matches the
     canonical `Button` example.
   - `Led::Init(pin, invert)` + `Led::Set(brightness)` + `Led::Update()` → on `Update()`, emits
     the matching declared LED's state (`lit = (brightness > 0) XOR invert`).
   - Capture point is `Update()` (libDaisy stages on `Set`, writes on `Update`); `SetLed` emits
     immediately.

3. **Switch shim — sampled at call time, no debounce thread (resolves R14).** `Switch::Init(pin,
   update_rate)` records the pin; `Debounce()` samples the IPC-backed atomic button state for
   that pin; `Pressed()` / `RisingEdge()` / `FallingEdge()` are computed relative to the previous
   `Debounce()` call — exactly the hardware contract, so the effect's own call rate governs edge
   detection (no separate ~1 kHz thread needed). Validate against `Button` (1 kHz loop).

4. **Button mode is a UI concern.** `momentary` = the UI reports *pressed* only while held;
   `toggle` = each click flips a latched pressed state. The runtime/shim only ever sees the
   resulting `pressed` boolean over IPC, so the shim is mode-agnostic.

5. **`active_level` is forward-compat metadata.** The virtual press is *logical*: `Pressed()`
   returns the UI press state directly. `active_level` is retained in the schema for hardware
   wiring fidelity (used by the M10b visual editor and the M12 hardware build); the emulator
   runtime does not invert on it.

6. **No standalone generic GPIO class in M10.** Scope is buttons (input via `Switch`) + LEDs
   (output via `SetLed`/`Led`). A general `GPIO::Read/Write` for arbitrary digital pins is
   deferred unless a later milestone needs it.

7. **Persistence (FR-CT-11).** `toggle` buttons persist their latched state across re-deploys
   (workspaceState, like pots); `momentary` buttons reset to released; LED indicators are
   runtime-driven and not persisted.

8. **IPC (04 §5, unchanged).** inbound `button {gpioPin, pressed}`, `buttonSnapshot {array}`;
   outbound `led {gpioPin, lit}`.
