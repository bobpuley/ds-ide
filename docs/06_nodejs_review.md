# Review Report

Scope: `./src` (Node.js/TypeScript, VS Code extension host + webview code), ~90 source files / 8,965 lines excluding tests. `tsconfig.json` runs with `strict: true`, `noUncheckedIndexedAccess: true`, `noImplicitOverride: true`, `noPropertyAccessFromIndexSignature: true` — a strong baseline reflected in generally clean type usage (no bare `any` found anywhere in `src/`). Findings below are grouped by checklist category, not by file, per review convention; a single file may appear under multiple categories.

---

## Type Safety

### Unsafe duplicated `el<T>()` DOM-lookup helper — no null check, type lies about non-nullability

#### Description
Five webview-context files independently redeclare the same helper for looking up DOM elements by id, casting away `document.getElementById`'s `| null` return type without checking it.

#### Evidence
```ts
function el<T extends HTMLElement>(id: string): T {
  return document.getElementById(id) as T;
}
```
Present near-identically in `controls-webview.ts:18-20`, `midi-webview.ts:6-8`, `oled-webview.ts:5-7`, `wiring-webview.ts:23-25`, `scope-webview.ts:4-6`. `scope-webview.ts` even mixes unguarded `el<T>()` results with defensive `?.` chains elsewhere in the same file (e.g. `sineFreqEl?.addEventListener`, line 204), tacitly admitting some lookups can fail.

#### Impact
A template/id drift (HTML id renamed but the script not updated, or vice versa) throws an uncaught `TypeError` at the first use of the "element" rather than at the lookup site, making the failure harder to diagnose. The non-null typing also suppresses the compiler's ability to catch this class of bug.

#### Affected Files
- src/webview/controls-webview.ts
- src/webview/midi-webview.ts
- src/webview/oled-webview.ts
- src/webview/wiring-webview.ts
- src/webview/scope-webview.ts

#### Recommended Fix
Consolidate into one shared browser-context utility (e.g. `webview-dom.ts`) that either throws a descriptive error on `null` (fail fast) or returns `T | null` and forces call sites to handle it.

#### Urgency Level
MEDIUM

### Unvalidated `JSON.parse` of data-island content, cast without runtime schema check

#### Description
Config/state data embedded by the extension host into `<script type="application/json">` data islands is parsed and cast to a type with no runtime shape validation.

#### Evidence
```ts
// controls-webview.ts:54-55
const _yamlInit = JSON.parse(_yamlInitEl ? _yamlInitEl.textContent || '{}' : '{}') as Partial<ControllerConfig>;
```
```ts
// wiring-webview.ts:38,41-42
const PIN_DEFS: PinDef[] = JSON.parse(el<HTMLElement>('pin-defs').textContent || '[]');
let wiredPins: WiredPin[] = JSON.parse(el<HTMLElement>('init-data').textContent || '[]');
let peripherals: PeripheralDisplayState[] = JSON.parse(el<HTMLElement>('peripherals-data').textContent || '[]');
```

#### Impact
Same-trust-boundary today (data is generated by the extension host's own `safeJson()`), so not attacker-controlled — but there's no defense if the two sides' types drift (a field renamed in `PinDef` without regenerating the HTML), and a missing/empty `textContent` (e.g. a template refactor that forgets the `id` attribute) silently produces `[]`/`{}` instead of surfacing an error.

#### Affected Files
- src/webview/controls-webview.ts:54-55
- src/webview/wiring-webview.ts:38,41-42

#### Recommended Fix
Add a light runtime shape check (or reuse a shared validator) before casting, and fail loudly (visible error state in the webview) rather than silently defaulting to an empty structure.

#### Urgency Level
MEDIUM

## Runtime Safety

### `EmulatorManager` "error" events have no listener in production code → uncaught throw can crash the Extension Host

#### Description
`EmulatorManager extends EventEmitter` and forwards socket/IPC errors via `this.emit('error', err)`, but `src/extension.ts`'s `activate()` never registers an `'error'` listener on the manager — only `'message'` and `'disconnect'` are wired up.

#### Evidence
- Emission sites: `src/emulator/manager.ts:383` (`client.on('error', (err: Error) => this.emit('error', err));`), `src/emulator/ipc-client.ts:61` (socket error) and `:109` (1 MB buffer-overflow error).
- `src/extension.ts:812` registers `manager.on('message', ...)`, `:842` registers `manager.on('disconnect', ...)` — no `manager.on('error', ...)` anywhere in the file (confirmed by grep across `src/`).
- Unit tests for `IpcClient`/`EmulatorManager` (e.g. `src/test/unit/emulator/ipc-client.test.ts:279,301`) do register `'error'` listeners, which is why this gap isn't caught by the existing test suite — the tests attach the very listener production code omits.

#### Impact
Node's `EventEmitter` special-cases `'error'`: if emitted with zero listeners, Node throws inside the process. Any raw socket error (ECONNRESET, EPIPE) or the deliberate buffer-overflow error can propagate through `IpcClient` → `EmulatorManager.emit('error', ...)` and throw with no handler, destabilizing or crashing the Extension Host for the entire VS Code window, not just this extension.

#### Affected Files
- src/extension.ts (activate(), missing `manager.on('error', ...)`)
- src/emulator/manager.ts:383
- src/emulator/ipc-client.ts:61,109

#### Recommended Fix
Add `manager.on('error', (err) => { void vscode.window.showErrorMessage(...); emulatorChannel.appendLine(...); })` alongside the existing `message`/`disconnect` handlers in `activate()`.

#### Urgency Level
HIGH

### Spawned emulator child process is not killed when the IPC handshake fails

#### Description
When `connectIpc()` rejects (connect timeout or a version-mismatch/malformed handshake), only `client.disconnect()` (closes the socket) runs — nothing kills the already-spawned `effect_emu` child process.

#### Evidence
`src/emulator/manager.ts:159-208`, specifically `onStdout` → `void this.connectIpc(match[1]!).then(resolve).catch(reject);` (line 182), and `connectIpc`/`awaitProtocolHandshake` at lines 360-447. The `.catch(reject)` path never calls `child.kill()`.

#### Impact
On a version-mismatch redeploy or a wedged handshake, a live emulator process (potentially holding CoreAudio device access) is orphaned until the next `deploy()` call's stale-PID reaper or clean extension `dispose()`. If VS Code exits abnormally first, cleanup depends entirely on the next session's `killStalePid`.

#### Affected Files
- src/emulator/manager.ts:159-208,360-447

#### Recommended Fix
Explicitly call `child.kill()` in the `connectIpc` rejection path before propagating the rejection.

#### Urgency Level
HIGH

### Unhandled promise rejection risk in `WiringViewProvider`'s message handler

#### Description
The `onDidReceiveMessage` callback is `async` and awaits three handler calls with no surrounding `try/catch`.

#### Evidence
`src/sidebar/wiring-editor-panel.ts:37-77` — `await this.onWirePin(...)` (line 50), `await this.onUnwirePin(...)` (line 63), `await this.onSetPeripheralEnabled(...)` (line 71). The real implementations (wired in from `extension.ts:590-`) perform file I/O (`findEffectSource`, `openTextDocument`, an edit + save). VS Code's `Event<T>` emitter does not await async listeners.
Contrast with `controls-editor-panel.ts`'s `onEditorSave` handler (`extension.ts:497-506`), which properly chains `.catch(err => vscode.window.showErrorMessage(...))`.

#### Impact
If the file I/O throws (permission error, missing file, malformed source), the promise rejects with nothing awaiting/catching it — an unhandled Node promise rejection with no user-facing error message, in a code path (wiring writes) that directly edits the user's source file.

#### Affected Files
- src/sidebar/wiring-editor-panel.ts:37-77

#### Recommended Fix
Wrap the three `await` calls in `try { ... } catch (err) { void vscode.window.showErrorMessage(...) }`, matching the pattern already used in `controls-editor-panel.ts`.

#### Urgency Level
HIGH

### `child_process` stdout/stderr handlers split logical lines across chunk boundaries, corrupting diagnostics and flash-success detection

#### Description
Both `hardware-build.ts` and `dfu-flash.ts` split each raw `'data'` chunk on `'\n'` independently, with no carry-over buffer for a line that spans two chunks.

#### Evidence
```ts
// hardware-build.ts:71-75
const handleData = (data: Buffer): void => {
  for (const line of data.toString('utf8').split('\n')) {
    if (line.trim()) onOutput(line);
  }
};
```
Node's `'data'` events on a pipe are not guaranteed to align with line boundaries.

#### Impact
In `hardware-build.ts`, a compiler diagnostic split across a chunk boundary fails to match `DIAG_RE` (`build-diagnostics.ts:7`) and is silently dropped from the Problems panel. In `dfu-flash.ts:113-122`, the same pattern detects `'File downloaded successfully'` in dfu-util output (used at line 130 to accept exit code 74 as success); if that string is split across chunks, a successful flash can be misreported as failed.

#### Affected Files
- src/commands/hardware-build.ts:71-75
- src/commands/dfu-flash.ts:113-122

#### Recommended Fix
Buffer partial data across `'data'` events — keep the trailing incomplete segment after the last `'\n'` and prepend it to the next chunk (standard line-splitting pattern).

#### Urgency Level
MEDIUM

### `killExisting()` uses SIGTERM only, with no SIGKILL escalation unlike `killStalePid`

#### Description
The live-child-process kill path lacks the SIGTERM→wait→SIGKILL escalation that the stale-PID kill path implements.

#### Evidence
```ts
// manager.ts:449-464
private killExisting(): void {
  this.intentionalDisconnect = true;
  if (this.childProcess) {
    this.childProcess.kill();
    this.childProcess = null;
  }
  ...
```
Contrast with `killStalePid` (`manager.ts:44-67`), which explicitly documents (FR-EXT-2) and implements SIGTERM → wait `KILL_ESCALATION_MS` → SIGKILL specifically to avoid zombies.

#### Impact
`killExisting()` runs on every redeploy and on `dispose()`. If the live `effect_emu` child ignores/misses SIGTERM (e.g. blocked in a native audio callback), it's never escalated to SIGKILL, and `this.childProcess` is nulled out regardless — possible lingering processes holding the audio device across rapid redeploys.

#### Affected Files
- src/emulator/manager.ts:449-464 (vs. 44-67)

#### Recommended Fix
Reuse the same SIGTERM/`KILL_ESCALATION_MS`/SIGKILL pattern (or a shared helper) for the live child in `killExisting()`.

#### Urgency Level
MEDIUM

### `HostMidiBridge.start()` has no exception guard around per-port `openPort`/`on` calls

#### Description
Only the initial port-count probe is try/caught; the per-port `openPort(i)` calls inside the subsequent loop are not.

#### Evidence
```ts
// host-bridge.ts:44-66
for (let i = 0; i < count; i++) {
  const input = this.inputFactory();
  input.openPort(i);          // can throw for a busy/disconnected device
  input.on('message', ...);
  this.openInputs.push(input);
}
```
Called unguarded from `src/extension.ts:586` (`hostMidiBridge.start();`), synchronously, not wrapped in try/catch.

#### Impact
RtMidi (behind the `midi` native binding) can throw if a port is already claimed by another process or disappears between enumeration and open. Such a throw propagates out of `start()` and, since it's called unguarded during `activate()`, out of `activate()` itself — aborting all subsequent command registrations, panels, etc. registered later in the function.

#### Affected Files
- src/midi/host-bridge.ts:44-66
- src/extension.ts:586

#### Recommended Fix
Wrap each `openPort`/`on` pair in its own try/catch so one bad port doesn't take down the whole bridge or block extension activation.

#### Urgency Level
MEDIUM

## Async / Concurrency

### `dispose()` racing an in-flight `deploy()` can leave a newly-spawned child unkilled

#### Description
`deploy()` assigns `this.childProcess = child` only after `spawn()` returns, which happens after several awaited steps. If `dispose()` runs in between, it finds `this.childProcess === null` and does nothing, but the deploy's `spawn()` call still executes afterward with nothing left to kill it.

#### Evidence
`src/emulator/manager.ts:132-221` (`deploy()`) vs. `354-358` (`dispose()`).

#### Impact
An orphaned emulator process from a deploy that raced extension teardown (e.g. closing the workspace right after issuing a deploy); relies on the next session's `killStalePid` for cleanup.

#### Affected Files
- src/emulator/manager.ts:132-221,354-358

#### Recommended Fix
Track deploy-in-progress state and either await/cancel the in-flight deploy lock inside `dispose()`, or re-check for teardown after `spawn()` before proceeding.

MEDIUM

## API Design

### `activate()` is a ~640-line god function doing everything

#### Description
A single function in `extension.ts` builds all stores, session state, the emulator manager, 4 output channels, the status bar, all webview view providers (with numerous inline callback closures), wires up manager events, debug adapter factories, `DeployCoordinator`, `runConfigProvider`, `initViewsFromProject`, and registers ~15 commands plus debug-session listeners plus a save-listener with ~45 lines of inline logic — all undecomposed.

#### Evidence
`src/extension.ts:380-1018`. `ControlsViewProvider` construction includes 8 inline callback closures (`485-537`); `WiringViewProvider` includes 3 large inline async callbacks (`588-745`); `ScopePanel` construction includes 7 inline callbacks (`747-810`); `workspace.onDidSaveTextDocument` handler has ~45 lines inline (`926-971`).

#### Impact
Very high cognitive load, hard to unit-test in isolation, high risk of accidental variable capture bugs across the huge closure, and any future contributor must read the whole function to understand a single wiring change. This is also the file where the two "unhandled 'error' event" and "effectSource ignored" bugs above live — a direct consequence of the file's size and lack of decomposition making cross-cutting gaps easy to miss.

#### Affected Files
- src/extension.ts:380-1018

#### Recommended Fix
Extract cohesive chunks (view-provider construction, command registration, save-listener logic, status/message routing) into named factory functions/modules that `activate()` merely composes.

#### Urgency Level
HIGH

### `ds-ide.effectSource` setting is silently ignored by the build command it's advertised for

#### Description
`build.ts` calls `findEffectSource(projectRoot)` with a single argument, so the "configured path" branch in `find-effect-source.ts` is always skipped — the entire config-driven resolution and its outside-workspace guard is dead code from this call site, even though the build failure message tells the user to use the setting.

#### Evidence
`src/commands/build.ts:24` calls `findEffectSource(projectRoot)` (one arg); `src/commands/find-effect-source.ts:35-51`'s `configured` parameter is therefore always `undefined`. `build.ts:26-29` on failure: `'ds-ide: no effect .cpp found ... Add one or set ds-ide.effectSource in settings.'`
Contrast: `src/extension.ts:48-61` defines a local wrapper that *does* read `vscode.workspace.getConfiguration('ds-ide').get<string>('effectSource')`, used for wiring-editor code paths (`extension.ts:210,289,302,577,592,658,689,886,949`) but never passed into `buildForEmulator` (called at `extension.ts:330,973`).

#### Impact
Any user who configures `ds-ide.effectSource` to disambiguate multiple/zero-heuristic-matched `.cpp` files will have the build command fail regardless, with an error message actively telling them to do something that has no effect on this code path. Confirmed via grep across `extension.ts`, not speculative.

#### Affected Files
- src/commands/build.ts:24
- src/commands/find-effect-source.ts:35-51
- src/extension.ts:48-61,330,973

#### Recommended Fix
Give `buildForEmulator` an optional `effectSrc`/`configured` parameter and thread the same config-reading/error-handling wrapper `extension.ts` already has into it, so build and wiring-editor commands share one resolution path.

#### Urgency Level
HIGH

## Testing

No dedicated testing-coverage gaps were raised as standalone findings during this review — the project maintains a `src/test/unit/` tree with close file-for-file parity against `src/` (test files exist for essentially every reviewed module), and several of the bugs identified above were traceable specifically because the corresponding *test* files register handlers (e.g. `'error'` listeners on `IpcClient`/`EmulatorManager`) that production code omits. That gap is itself worth calling out:

### Existing unit tests mask a production gap by registering handlers production code doesn't

#### Description
Unit tests for `IpcClient`/`EmulatorManager` register `'error'` event listeners to make assertions, which means the test suite never exercises the "zero listeners attached" scenario that causes the HIGH-severity uncaught-throw finding above.

#### Evidence
`src/test/unit/emulator/ipc-client.test.ts:279,301` register `'error'` listeners; `src/extension.ts` never does in production.

#### Impact
The test suite passing is not evidence that the production `activate()` wiring is complete — a false sense of coverage on the exact code path most likely to crash the Extension Host.

#### Affected Files
- src/test/unit/emulator/ipc-client.test.ts
- src/test/unit/emulator/manager.test.ts
- src/extension.ts

#### Recommended Fix
Add an integration-style test that activates the extension (or constructs `DeployCoordinator`'s manager wiring as `extension.ts` does) and asserts an `EmulatorManager` `'error'` emission does not crash the process/produces a handled user-facing message.

#### Urgency Level
MEDIUM
