## v20 notes

- **FR-HW-5 (hardware memory-budget alerting):** architecture impact.
  - New parser module `src/diagnostics/memory-region-diagnostics.ts`, alongside (not merged into) `build-diagnostics.ts` — the region table is a different shape of data (a full post-link summary, not per-line `file:line:col` diagnostics) and keeping it separate avoids overloading `parseBuildLine()`'s regex-per-line contract. Exposes: `parseMemoryRegionTable(output: string): MemoryRegion[]` (region name, used size, region size, %age used), `extractOverflowError(output: string): { region: string; overflowBytes: number } | undefined` (precise match) plus a fallback substring check (`output.includes('overflowed')`) for the lower-confidence message.
  - `buildForHardware()` (`src/commands/hardware-build.ts`) gains a post-build step: on failure, try `extractOverflowError()` first (precise message), then the `overflowed` substring fallback, before falling back to today's generic `make exited with code N`; on success, call `parseMemoryRegionTable()`, print the table to the output channel, and check the ≥75% threshold and the `hardwareVariant='base'` + `SDRAM used > 0` hard-error rule (reads `vscode.workspace.getConfiguration('ds-ide', <project folder Uri>).get('hardwareVariant')`, resource-scoped so it resolves per project folder like `ds-ide.armToolchainPath`).
  - New `ds-ide.hardwareVariant` setting added to `package.json`'s `contributes.configuration` (enum `['base', '65mb-sdram']`, default `'base'`, resource-scoped — unlike `ds-ide.effectSource`'s window scope, this genuinely varies per physical project/board so per-folder resolution is correct here).
  - `buildForHardware()` also gains an unset-check at entry: if `ds-ide.hardwareVariant` has no value for the project folder, prompt once via `vscode.window.showQuickPick` (same question/options as the wizard) before proceeding; on accept, write the answer to that folder's `.vscode/settings.json` via `vscode.workspace.getConfiguration(...).update(..., vscode.ConfigurationTarget.WorkspaceFolder)`; on dismiss, use `'base'` for that build only without persisting, so the prompt reappears next build.
  - `createEffectProject()` (`src/commands/create-effect-project.ts`) gains the same hardware-variant prompt after the existing template-file writes, persisting into the newly-created project's `.vscode/settings.json` (created fresh, since a brand-new project has none yet).
  - No change to `dfu-flash.ts`, the project Makefile, or `APP_TYPE` handling — explicitly out of scope for this requirement (see deferred idea in `01_input-ideas.md`).

- **FR-PKG-3 (wizard-time DaisySP provisioning):** architecture impact. ds-ide's own repo adds DaisySP as a git submodule (e.g. `vendor/DaisySP/`), pinned to a specific upstream tag/commit — mirroring how DaisySP is normally consumed in Daisy projects, and making version bumps an explicit, reviewable "update submodule pointer" change rather than a silently-forgotten manual copy step. The extension's packaging step (`.vscodeignore`/`vsce package` config) must include `vendor/DaisySP/Source` in the shipped `.vsix` alongside `emulator/`. `createEffectProject()` (`src/commands/create-effect-project.ts`) gains a provisioning step after the existing template-file writes: copy `vendor/DaisySP/Source` (resolved from `extensionPath`, read at copy time — not symlinked, since `extensionPath` is not stable across ds-ide versions) into the new project at `<project>/DaisySP/Source`, using `vscode.workspace.fs.copy(..., { recursive: true })`. No change to `EmulatorManager`/`detectDaisySP()` — the copied directory is indistinguishable from a manually-symlinked or submoduled one once it lands at that conventional path.
