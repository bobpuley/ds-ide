OLED Embedding — evaluation notes

Variant A — tabbed

  • Preview gets the full panel height (220px) — legible at a real usable scale.
  • "Defaults to Preview when OLED is enabled" (per the requirement) maps directly onto which tab opens first — no extra state to design.
  • Extends cleanly to future preview surfaces (pedal/board/rack): each just becomes another tab, or the Preview tab's content switches on what's enabled.

Variant A — trade-off

  • Can't see the OLED and drag a control's position at the same time — you switch tabs.

Variant B — docked strip

  • Layout and preview are both visible simultaneously — useful if a control's behavior is meant to be checked against the OLED output while placing it.

Variant B — trade-off

  • Preview is cramped (~130px) — a 128×64 display only reads clearly around 2x scale.
  • Doesn't scale to future preview surfaces: a second docked strip (e.g. a pedal graphic) stacks on top of this one, eating canvas height every time something new is added.
  • Canvas area shrinks whenever `oled` is enabled, even while the user is only doing layout work and not looking at the strip.

Open questions

  • Both variants keep the pop-out ("↗") affordance opening today's unchanged standalone OledPanel — confirm that's still wanted once embedded, or whether pop-out becomes redundant for most workflows.
  • "Enabled, no frame yet" state shown here as a dim canvas with a caption — good enough, or should it show the last frame from a previous run if one exists?
