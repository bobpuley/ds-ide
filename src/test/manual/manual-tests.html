ds-ide — Manual Test Tracker

Manual verification checklist for use cases that are hard to validate with unit tests. Run after each implementation that touches a related area. Click a status control to preview a result while testing.

Emulator build → run inner loop

The core edit→build→run loop must stay fast and require no source changes to target the emulator (AC-1, AC-7, non-negotiable: "Speed is the product").

Steps

  1. Open a ported effect (e.g. tremolo) unmodified from its hardware source.
  2. Run "Daisy IDE: Build for Emulator", then Start.
  3. Make a small DSP parameter change, save, and re-run the loop.
  4. Time from save to audio running again.

Expected result

Builds and deploys without any source edits; audio starts running on Start; the full edit→…→recompile loop completes in under 30 seconds for a small change.

On-screen potentiometer changes affect output (ADC)

Simulated ADC input via on-screen pots must visibly reach the effect's audio callback (AC-2).

Steps

  1. Run an effect that reads a pot (e.g. feedback/mix control) and watch the scope panel.
  2. Drag the on-screen pot through its full range while audio is running.

Expected result

The scope's output waveform visibly changes in response to the pot movement, tracking the pot's position with no perceptible lag.

Breakpoint in audio callback freezes simulated time

Debugging must pause the audio callback with time frozen, not just halt execution (AC-4).

Steps

  1. Set a breakpoint on a line inside the audio callback.
  2. Start debugging; let the breakpoint hit.
  3. Confirm the paused line is shown in the editor.
  4. Wait several seconds at the breakpoint, then Continue.
  5. Stop the session.

Expected result

Breakpoint hits and highlights the correct line; while paused, simulated audio time does not advance (no dropped/skipped samples on resume); Continue resumes cleanly; Stop ends the session without hanging.

NaN/clipping bug is flagged, not just inaudible

Some DSP bugs (denormals, NaN propagation, silent clipping) are easy to miss by ear but must be surfaced explicitly (AC-5).

Steps

  1. Introduce a deliberate divide-by-zero or feedback-runaway bug into a test effect's audio path.
  2. Run the effect in the emulator and observe the output panel/diagnostics, not just by listening.

Expected result

ds-ide flags the NaN/clipping condition explicitly (diagnostic, warning banner, or scope indicator) even if the resulting audio glitch would be easy to miss by ear alone.

Real audio I/O: live host input + speaker output

Beyond the sine generator, the emulator must support real host audio input and speaker output.

Steps

  1. Switch the emulator's input source from sine to live host audio input (e.g. a connected interface or built-in mic).
  2. Enable host speaker output.
  3. Play/speak into the input and listen to the processed output through speakers.

Expected result

Live input is audibly processed by the effect and heard through the host speakers with no dropouts or excessive latency during normal use.

Hardware build still works untouched

ds-ide must never break the standard external hardware build path (AC-6, non-negotiable: "Don't break the hardware path").

Steps

  1. Take an effect that has been built and run in the emulator.
  2. Run "Daisy IDE: Build for Hardware" without modifying the source.
  3. Confirm the produced .elf/.bin is a valid ARM cross-compiled artifact.

Expected result

The hardware build succeeds against the same unmodified source used for the emulator build, producing a flashable artifact.

DFU flash to physical Daisy Seed

The built hardware artifact must actually flash to and run on real Daisy Seed hardware.

Steps

  1. Connect a Daisy Seed in DFU/bootloader mode.
  2. Run the DFU flash command from ds-ide.
  3. Power-cycle or reset the board and confirm the effect runs on real hardware.

Expected result

Flash completes without error and the effect audibly runs correctly on physical hardware, matching emulator behavior.

Hardware variant prompt (first build) and persistence

FR-HW-5d: the wizard/hardware-build flow should prompt once for the hardware variant and remember the choice.

Steps

  1. Create a fresh effect project or clear ds-ide.hardwareVariant from workspace settings.
  2. Run "Daisy IDE: Build for Hardware" for the first time.
  3. Pick a variant (e.g. "65mb-sdram"); rebuild and confirm no re-prompt.
  4. Decline the prompt once on a different project and confirm it re-prompts next build.

Expected result

Prompt appears exactly once per project when unset; the chosen variant persists across rebuilds; declining uses "base" for that build only and prompts again next time.

Hardware memory-budget alerting (near-limit + SDRAM mismatch)

M61: hardware builds should warn near memory limits and hard-error on SDRAM usage that doesn't match the board's physical hardware.

Steps

  1. Build a hardware-target effect with a buffer sized to ~85% of a region's capacity (e.g. SRAM).
  2. Build another with a large buffer placed in DSY_SDRAM_BSS while ds-ide.hardwareVariant is set to "base".

Expected result

First case: build succeeds with a "near limit" warning naming the region and percentage. Second case: build fails/hard-errors, explicitly stating the base Daisy Seed has no physical SDRAM chip.

Controls Editor: wiring a pot stays in sync with code

Visual control wiring must round-trip correctly with the source code's controls convention annotations.

Steps

  1. Open the Controls Editor / Wiring Editor for an effect with an unwired pot.
  2. Drag-wire a potentiometer to a physical pin.
  3. Inspect the generated code annotation, then edit the pin in code directly and reopen the editor.

Expected result

Wiring the pot in the UI updates the source annotation correctly; editing the annotation directly in code is reflected back in the editor on reopen, with no drift between the two.

Wiring Editor: pin conflict detection

Two devices claiming the same physical pin must be caught and surfaced in the UI, not silently accepted.

Steps

  1. Wire a pot to a given physical pin.
  2. Wire a second, different device (e.g. a button or LED) to that same physical pin.

Expected result

The Wiring Editor visibly flags the conflict (e.g. highlighted pin, warning message) rather than silently allowing two devices on the same physical pin.

MIDI: on-screen keyboard and host MIDI bridge reach the effect

FR-DEV-18: on-screen keyboard, message monitor, and host MIDI bridge (macOS) must actually deliver events into the running effect.

Steps

  1. Run a MIDI-enabled effect (e.g. tremolo-filter-midi) in the emulator.
  2. Play notes on the on-screen keyboard; send a Control Change and a Program Change.
  3. Connect a real/virtual MIDI source via the host MIDI bridge and repeat.
  4. Watch the MIDI monitor panel while doing all of the above.

Expected result

Note On/Off, Control Change, and Program Change events audibly affect the running effect and appear correctly in the MIDI monitor panel, from both the on-screen keyboard and the host MIDI bridge.

OLED panel renders the simulated SSD1306 framebuffer

FR-DEV-15: the OLED viewer must accurately mirror what the effect draws to a simulated SSD1306 display.

Steps

  1. Run an effect that draws text/shapes to the OLED display each frame.
  2. Open the OLED viewer panel and watch it while the effect runs and while a bound pot changes on-screen content.

Expected result

The OLED panel accurately mirrors the framebuffer in real time, including updates driven by control changes, with no visible tearing or stale frames.

Session recording captures and replays audio

Recorded sessions should capture real audio I/O and play back deterministically.

Steps

  1. Start a recording session while driving the effect with pots and/or MIDI.
  2. Stop the recording and replay it.

Expected result

Replay reproduces the same audio output and control movements as the original run, without manual re-driving of controls.

SD card viewer browses a simulated microSD card

FR-DEV-45-area: SD card device support should let a developer inspect files on the simulated card.

Steps

  1. Configure an effect that reads/writes files via the simulated SD card device.
  2. Open the SD card viewer panel while the effect runs and after it writes a file.

Expected result

The viewer correctly lists files present on the simulated card and reflects new files written during the run without requiring a restart.

Scope and spectrum panels track real-time audio

Waveform and FFT visualization must accurately and responsively reflect the live audio signal, not a stale snapshot.

Steps

  1. Run an effect and open both the scope and spectrum panels.
  2. Change input frequency/amplitude (sine generator settings or live input) and watch both panels update.

Expected result

Both panels update smoothly in real time; the spectrum panel's frequency peaks match the actual input/output content with no lag or frozen display.

Scope chips: open and close each popover (FR-SCI-15, FR-SCI-16)

Gain, Scale, Trigger, frequency axis and level mode are one chip each; clicking opens a popover of choices.

Steps

  1. Run an effect and open the Scope panel.
  2. Click each of the five chips in turn; pick a value, then reopen and close with Esc, with a click outside, and by clicking the chip again.
  3. With a popover open, use ↑/↓ and Enter; press Space with a chip focused.

Expected result

Each popover opens under its chip with the current value ticked (✓). A pick closes it and updates the chip text and the plot. Esc returns focus to the chip. ↑/↓ move between entries and Enter picks. Space on a focused chip does not freeze the display; Space elsewhere still does.

Scope Trigger chip: two-step choice (FR-SCI-16)

The Trigger popover has Edge and Source groups; Source only applies once an edge is chosen.

Steps

  1. Open the Trigger chip while it shows Free: Source entries are dimmed.
  2. Pick Rising: the popover stays open and Source becomes available. Pick L.
  3. Reopen and pick Free.

Expected result

After Rising + L the chip reads ↗ L in amber with a ●; the popover stayed open after the edge pick. Back at Free the chip reads Free with no ●.

Scope chips: non-default marker (FR-SCI-17)

A chip that is not at its default is marked.

Steps

  1. Set Gain ×4, Scale dBFS, Lin Hz and Relative.
  2. Set each back to ×1, Linear, Log Hz and Absolute dBFS.

Expected result

Changed chips show a ● and amber text; chips at their default show neither. A screen reader announces “(changed from default)” on changed chips.

Scope popover flips above in a short panel (FR-SCI-16)

The popover must not run off the bottom of the viewport.

Steps

  1. Make the Scope panel very short (drag the panel divider) so the Spectrum bar is near the bottom.
  2. Open the Level mode and Frequency axis chips.

Expected result

The popover opens above the chip when there is no room below, and is never cut off at the left or right edge.

Scope toolbar fits one row beside code (FR-SCI-15)

With chips, the toolbar needs far less width than the old segmented buttons.

Steps

  1. Open the Scope panel in a split beside the code editor and drag it to about 560 px wide.

Expected result

The toolbar (Time, Freeze, 1× Single, Gain, Scale, Trigger, snapshot, CSV) stays on a single row; the spectrum bar's two chips also fit on one row.

Scope popover legibility in dark, light and high-contrast themes (FR-SCI-16)

The popover is opaque and uses the theme's dropdown colours.

Steps

  1. Open any chip's popover under a dark, a light and a high-contrast theme.

Expected result

Entries, the ✓, group titles and dimmed entries are legible in all three themes, and the plot behind the popover does not show through.
